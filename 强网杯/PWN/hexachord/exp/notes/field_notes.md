# Hexachord：终章石碑案卷

## 现场封存

本案的目标服务位于 `47.95.113.113:20549`。它让同一条连接依次经历二十个乐章；征服一章便取得一枚残章，终局才给出 `flag.enc`。一次已完成的会话在第 15 章未取得残章，第 20 章开始时已达到所需数量，于是直接离开，结算为 **18/20**。终局原文中的关键部分如下：

```text
[*] 演奏落幕：集得残章 18/20 枚
[*] 终章石碑 flag.enc: 80f3ff3c022c74662906117c8571e8b99e26bb5c6d509b9b1395de29864f8fdc5e4bb80c8a9430ee710c89fdfac1b53a663408f83230e0d38ee87e36478dfe59e4ce2d281e7f
[*] 碑文已现。持残章者，自会懂得如何解读它
```

密文不是每章的奖励；每章得到的是一条 66 位十六进制残章记录。取到密文却只有十几条记录，无法完成终章。下面按现场证物倒推，记录这 18 条记录是怎样取得的。

## 证物 A：一段同时扮演两种角色的咒文

每章先展示 40 字节的 `target`，菜单 4 接收至多 31 字节咒文。校验器按字节模 6 的余数把咒文解释为 `U/R/F/D/L/B` 六面转动，要求魔方终态与 `target` 一致；校验通过后，同一串字节又作为 x86-64 指令执行。因此只会解魔方还不够：算出的公式还必须能选出具有所需余数的机器码字节。

复现包先用预计算表搜索不超过 31 步的公式，再尝试几种编码过的栈迁移入口。成功会话中的记录既有普通搜索所得的 `identity`，也有强表搜索所得的 `compact-identity`；咒文使用过 `pop-pop-rsp-ret` 和 `pop-pop-rbp-leave-ret` 两种入口。它们的共同目的，是把短咒文的控制流交给菜单 1 已保存的较长祷文，而不是把整条链塞进 31 字节。

## 证物 B：卷轴、祷文与父进程

菜单 1 可保存 112 字节祷文。菜单 2 的路径输入可达到 255 字节，足以在栈上布置枢轴所需的地址；路径输入中偏移 `0xf0` 的槽位承担这个任务。先读 `/proc/64/auxv`，由 `AT_PHDR` 与 `AT_BASE` 算出每章的主程序和加载器地址，再据此拼装祷文与栈上的地址。地址随章节变化，不能把上一章泄漏值照搬到下一章。

服务执行合格咒文时会 fork 出子进程。第一段祷文调用 `mprotect`，随后运行短代码，清除子进程 BSS 中的 `tuned`、`read_once`、`spell_once` 标记；再以 `process_vm_writev` 把修改后的页写回等待中的服务父进程。这样同一章内还能第二次调弦、翻阅和弹奏。只重置子进程自身不会恢复父进程的菜单状态。

## 证物 C：把不可直读的文件改名给菜单看

第二段祷文通过系统调用建立 `/flag` 到 `/tmp/x` 的符号链接。菜单 2 对含 `flag` 的路径会拦截，但这次输入仍可完成栈上槽位布置，且不会用掉随后读文件的机会。第二次弹奏成功后，菜单 2 读取 `/tmp/x`，得到 66 个十六进制字符。离开该章，外层才确认“残章到手”。

用同样的链接办法可取回 `/gift`。这个程序说明终章密钥如何分给各章：32 字节密钥的每个字节都对应一个 17 次多项式，二十章分别给出一组取值。因此需要同一连接中的任意 18 条有效记录。每条记录由 1 字节章号和 32 字节取值组成；开头的章号字节只用于标识来源，在插值时不直接使用。将通过外层计分的记录按取得顺序排好，第一条到第十八条依次取 Shamir 横坐标 `x=1..18`，纵坐标取后面的 32 字节。即使中间有一章空缺，计分顺序仍是连续的。

本案的账本里，第 1 至 14 章和第 16 至 19 章计分，第 15 章跳过，第 20 章在达到 18 枚后离开。整理时仍把第 16 章得到的记录放在第十五个有效位置。账本应同时保留原始 66 位十六进制文本与计分状态，避免将未计分的读取结果混入这 18 条。

## 终章计算单

插值在 GF(256) 上逐字节进行。此处采用约简多项式 `0x11d`，实现 `xtime` 时最高位溢出的异或常量为 `0x1d`；加法是异或，乘法和除法均在同一个域内完成。对任意一个密钥字节，用十八个点在零处作拉格朗日插值：

```text
K[b] = XOR_j ( y[j,b] * PRODUCT_{m != j} x[m] / (x[m] XOR x[j]) )
```

得到 32 字节密钥后，把 `flag.enc` 的原始字节依次切成 `12 字节 nonce || 密文 || 16 字节 tag`，用 AES-256-GCM 解密并验证 tag。下面的归档片段明确了横坐标与域乘法的约定；其余搜索、ROP 和收包逻辑由复现包脚本承担。

```python
def xtime(value: int) -> int:
    return ((value << 1) ^ (0x1d if value & 0x80 else 0)) & 0xff

def archive_points(fragments: list[bytes]) -> list[tuple[int, bytes]]:
    # fragments 按“残章到手”的先后顺序排列；首字节是来源标签。
    return [(order, fragment[1:])
            for order, fragment in enumerate(fragments, start=1)]
```

## 复核路线

先在复现包目录安装 `requirements.txt`，再以当前端点运行：

```bash
python3.14 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m hexachord_lab check
.venv/bin/python -m hexachord_lab capture --host 47.95.113.113 --port 20549 --out runs/attempt_01
```

建表会占用较多内存；脚本在连接前完成准备，章节中再限时求解。检查每轮 `chapters.jsonl`：至少 18 条记录应有 `credited` 或 `final_received` 状态，每条残章须是完整的 66 位十六进制文本，结算要出现 `18/20` 和 `flag.enc`。残章与结算密文必须来自同一条 TCP 会话。

若 AES-GCM 报 tag 校验失败，先从传输链路排查：对照原始 `transcript.bin` 与逐章记录，确认没有少收一个字符、把未计分的文件回显当残章，或把另一轮连接的记录混入本轮。只有 GCM 校验通过，明文才可作为最终提交值。
